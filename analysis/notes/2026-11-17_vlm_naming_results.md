A later run of a model is used only for cost on its own hardware and for the agreement of its names with the primary run. Every cost row names its site and GPU; numbers of different sites are never combined. The design question (phone plus a local workstation) is answered by the RTX 4090 rows where they exist; the cluster rows compare all four contestants on one GPU type.

## Changes after the design was fixed

Made before any contestant or judge had produced a result on FindBack data:

1. Two counts in the design note were corrected after the package was built: the cross-view set has 54 crops (not 74; the earlier figure counted detections of entries dropped at the end of the scan) and the 960-px cap affects 2 records (not 3).
2. The workstation folder was reorganised into the fixed layout `data/ code/ models/ env/ runs/<date>_<name>/ scratch/` at the user's request (moves only; no file content changed).
3. Shared-machine rules were tightened after another account's process appeared on both GPUs: a GPU is used only when no process of anyone is on it (so the 90% memory setting stays), a run starts after at least 10 free minutes (polls every 5 minutes), a session finishes the item in flight and stops when another account's process appears, interrupted attempts are kept aside as contaminated and repeated, and every process is limited to 4 CPU threads. The thread limit only affects the CPU side (request handling and image preprocessing) and was set before any timing was taken. For Model A this rule was replaced by item 5.
4. The sessions run in a detached queue on the workstation (so that a free window at night is used even when the Mac sleeps), and the round trip from the Mac therefore runs in a separate short session per model instead of at the end of each naming session. The judging pool is built on the workstation by the same function as on the Mac.
5. Shared-GPU mode (2026-11-17, about 23:15, decided with the user; details in the design note's dated deviation): Model A ran on one GPU shared with another account's idle process, under a memory cap leaving at least 5 GiB unreserved, with a fixed 1 GiB KV cache, 4,096 batched tokens and multimodal profiling at 960 × 960 instead of the fixed 90% memory setting. A watchdog sampled the other process every 0.1 s for the first 5 minutes and then once a second, and would have stopped our server at any sign of activity. The answers are not expected to depend on these memory settings (the inputs and preprocessing are unchanged); the timings and energy are labelled as shared-GPU numbers.

A smoke test on a synthetic image (no home photo) checked the server, the structured output and the metric names before the runs; its output is not used.

Made after the Model A naming results had been read (none of them changes a prompt, an input, a metric or a naming result):

6. The watchdog now also stops our server when it cannot read the GPU state for 5 s (before, it kept running without a reading). The Model A naming session ran with the earlier code; its watchdog log has 2,980 readings and no gap longer than 1.02 s.
7. The round trip from the Mac can run in shared-GPU mode (`vlm_ws.py roundtrip MODEL --shared`), with the same cap and watchdog as item 5.
8. The first shared round-trip session waited in its hold state for about 9 minutes because the Mac-side launch call did not return (a shell detaching bug, since fixed in `vlm_ws.py`). The round trip was then run by hand with the same function against the held server and the session was released. The measurement itself is unaffected; the session's energy log covers the idle wait and is not used.

Made on 2026-11-18 (about 00:00 to 00:40), before any session on the cluster had produced a result; Model A's workstation names had been read:

9. **A second site.** Another account's process kept both workstation GPUs, so with the user's permission the remaining sessions ran on a university Slurm cluster: Model B, Model C and Model D, a second run of Model A, the judging pool and both judges. Every contestant session there ran on the same GPU type (NVIDIA H200 NVL), one whole GPU per batch job, with the design's serving settings unchanged; on this GPU the fixed `--gpu-memory-utilization 0.90` reserves a much larger KV cache than on a 24 GB card, which affects memory and possibly batching headroom, not the requests. Each session is one batch job that does not depend on the Mac; the round trip from the Mac exists for the workstation only. The cluster's cost numbers are reported in their own rows with the site and GPU, never combined with the workstation's, and the design's question (phone plus a local workstation) is answered by the RTX 4090 rows where they exist.
10. **Which run counts (fixed before any cluster result).** A model's primary run is its first complete run in time at any site. For Model A that is the workstation run of 2026-11-17 (shared GPU); for the others, their cluster runs. Naming quality, the label-free signals and the judging pool use primary runs only. A later run of a model (Model A on the cluster; workstation runs if its GPUs free up later) is used only for cost on its own hardware and for the agreement of its names with the primary run. Model A's cluster run uses the design's own-GPU settings, unlike its shared-GPU workstation run.
11. **Judging on the cluster.** Each judge job builds the blind pool itself from the primary runs (the workstation run's names are copied as text; the same function as on the Mac), keeps it in its run folder, and the report uses a judge run only when that pool equals the pool it rebuilds from the primary runs. Judge B runs on one H200 NVL GPU (141 GB) instead of two GPUs with tensor parallelism: the design allowed dropping it when two GPUs were not free; running it on one large GPU changes only the tensor-parallel size, not the prompt, pool, weights or any other setting.
12. **Software on the cluster.** The same pins as on the workstation (vLLM 0.33.0, nvidia-ml-py 13.615.71) under the cluster's Miniconda Python 3.12.8 (the workstation's environment was also built on a Miniconda Python 3.12; a first attempt with the cluster's other Python 3.12 build failed because that build lacks `ctypes`, which torch needs), installed with uv instead of pip because the package index gave about 5 MB/s per connection there and pip downloads one file at a time; the unpinned dependencies were resolved on 2026-11-18. The workstation's exact versions of unpinned packages were not recorded, so they may differ; each cluster run folder keeps its own `environment.txt` (Python, driver, package list).
13. **Storage and downloads on the cluster.** One private folder (mode 700) on the cluster's work storage, the workstation's layout plus `jobs/`; a disk budget of 130 GB for the weights (about 102 GB for all six; the environment and caches add about 20 GB) with every model's weights kept until the end; weights downloaded by CPU batch jobs (up to 8 files at a time, over plain HTTPS because Hugging Face's Xet transfer reached only about 8 MB/s there against about 54 MB/s per file) from the publishers' repositories at the pinned revisions. In a job the session checks that NVML sees exactly the GPU Slurm allocated, and uses GPU index 0. Time limits: 60 minutes per naming session and 75 per judge (raised from 45 before any judge started, when start-up turned out to take about 15 to 20 minutes on the cluster); the session's own limit follows the job's.
14. **Model names kept private (the user's request).** The repository and the cluster name the models only by aliases (Model A to D, Judge A and B; keys `model_a` ... `judge_b`), with a rough size class, licence and generic precision. The repositories, pinned revisions and serving limits moved unchanged to a git-ignored file read at run time (`analysis/vlm_models.private.json`; on the cluster a copy inside the private folder). The served model name is now the alias (it appears only in the request's routing field, not in any prompt), and the server is started as `python vlm_remote.py serve <run>/serve_args.json` on a neutral weights path (`models/<alias>`, a link to the pinned snapshot), with the same arguments as before, so that the queue, job details and process lists that other users of the cluster can see name no model. Before this rule arrived, queued jobs whose names contained model family names (not repositories or versions) were visible in the cluster's queue for about seven minutes; they were cancelled before any of them started and resubmitted under the aliases.
15. **A CUDA compiler in the cluster jobs (01:40 to 02:08).** vLLM JIT-builds FlashInfer's sampling module during the server's warm-up (the workstation's log shows the same build). The first Model A attempt on the cluster stopped because the job had no CUDA compiler; with the cluster's CUDA 13.0 compiler on the path, a Model C attempt then stopped because the module, built by the cluster's newer default C++ compiler, needed a newer C++ runtime than the one the environment's Python had already loaded. The jobs now build with the system compiler, whose C++ runtime matches; only the compiler is put on the path, not the toolkit's libraries, so torch keeps its own CUDA 13.0 libraries. The module was built once before the sessions. Greedy requests (temperature 0) do not use that sampler, so the answers do not depend on it. The four sessions running at that moment were cancelled during start-up, before any of them had produced a result, and resubmitted with the same settings. Later (02:15), the first Model D attempt stopped because its 4-bit kernels are compiled at run time through NVRTC, which did not find its own builtins library; the server now gets the environment's CUDA 13.0 library folder (the files torch already loads) on its library path. Model D's job was cancelled while it retried with the first listed setting and was resubmitted with the design's settings. The failed and cancelled attempts and a software test on a synthetic image on another GPU type (stopped by its own time limit during start-up; no home photo, output not used) are kept aside and named in the results note. From then on, a server that fails for a reason of the environment (a missing compiler, an import error, a library that does not load, a driver mismatch) is not retried with the listed settings and never counts as the model not starting.
16. **Start-up on the cluster.** Importing the Python environment from the cluster's network file system took 15 to 20 minutes per server start, so each job unpacks an archive of the same environment onto node-local storage first (about 10 seconds) and runs from there; the weights are still read from the network file system. Every session whose numbers are reported ran this way. The cluster's start-up times are therefore not comparable with the workstation's.

Made on 2026-11-18 (about 02:35 to 02:45), after Judge A's verdicts had been read (no prompt, input, pool, model or naming result changed):

17. **Judge A could not judge the items with two images.** Every Judge A request for an S-frame item (crop plus marked keyframe, the design's view; 36 of its 88 requests) was rejected by the server before the model saw it: in this environment (vLLM 0.33.0 with transformers 5.20.2) the judge's image processor cannot return two images of different sizes in one request (reproduced off the GPU on two synthetic images: `stack expects each tensor to be equal size`). Its one-image requests (26 items: the tapped records and the scan entries without a saved keyframe) were all answered. Judge B, with a different image processor, answered all 88. Neither the judge's view nor the software was changed to work around this, because doing so after reading results would have changed the judging; instead the report treats an item whose request failed as missing data (left out of that judge's cells, each cell giving its own n) rather than as a name judged not right, which the design's rule ("unclear and no name count as not right") does not cover. Between-judge agreement and the ranking check use the items both judges judged.
18. **The plot uses Judge B.** The design's plot shows the primary judge's strict score on S-frame, but Judge A has no verdict on any S-frame item, so the plot and its number table use Judge B (named in the plot and the note). Judge A's own numbers stay in the tables for the items it judged.

Made on 2026-11-18 after all results had been read (no prompt, input, pool, model, verdict or number changed):
